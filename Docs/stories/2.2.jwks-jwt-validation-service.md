# Story 2.2: JWKS Provider and JWT Validation Service

## Status
Draft

## Story
**As a** backend developer validating Dynamic.xyz JWT tokens,  
**I want** a JWKS key provider with caching and comprehensive JWT validation service,  
**so that** I can securely validate Dynamic.xyz JWT tokens using Microsoft.IdentityModel.Tokens with proper key rotation support.

## Acceptance Criteria

1. Create `IJwksKeyProvider` interface and `JwksKeyProvider` implementation with memory caching
2. Implement `IJwtValidationService` interface and `JwtValidationService` with comprehensive token validation
3. Use `IMemoryCache` for JWKS key caching with configurable expiration (10 minutes default)
4. Validate JWT tokens using Microsoft.IdentityModel.Tokens with proper issuer and signature verification
5. Extract Dynamic.xyz specific claims from validated JWT tokens into `DynamicJwtPayload` model
6. Handle JWT validation errors with appropriate Axon `Result<T, Error>` patterns
7. Implement proper clock skew tolerance (5 minutes default) for token expiration validation
8. Use separate JWKS HttpClient for fetching public keys from Dynamic.xyz JWKS endpoint
9. Register all services in the Identity infrastructure module with proper DI lifetimes
10. Build passes with comprehensive error handling and no warnings

### JWKS Architecture Requirements  
[Source: FRD S2 Section 6.1, JWKS Provider Implementation]

**JWKS Key Provider Specifications:**
- Use separate "JwksClient" HttpClient (10-second timeout, no authentication)
- Cache raw JWKS JSON string in IMemoryCache with key "jwks_keys"
- Default cache duration: 10 minutes (configurable via JwtValidationOptions)
- Fetch from `{BaseUrl}/sdk/{EnvironmentId}/.well-known/jwks` endpoint
- Parse using `JsonWebKeySet` class from Microsoft.IdentityModel.Tokens
- Return `IList<SecurityKey>` for token validation

**Caching Strategy:**
```csharp
// Cache-first approach with fallback
if (_cache.TryGetValue<string>(CacheKey, out var cachedJson) && !string.IsNullOrEmpty(cachedJson))
{
    // Parse cached JWKS and return keys
    var cachedKeySet = new JsonWebKeySet(cachedJson);
    return cachedKeySet.GetSigningKeys();
}
// Fallback: Fetch fresh from Dynamic.xyz
```

### JWT Validation Requirements
[Source: FRD S2 Section 7.1, JWT Validation Implementation]

**TokenValidationParameters Configuration:**
- `ValidateIssuerSigningKey`: true (use JWKS keys)
- `IssuerSigningKeys`: Retrieved from IJwksKeyProvider  
- `ValidateIssuer`: true with `ValidIssuer`: `https://app.dynamic.xyz/api/v0/sdk/{EnvironmentId}`
- `ValidateAudience`: false (Dynamic.xyz doesn't use audience)
- `ValidateLifetime`: true with configurable ClockSkew
- `ClockSkew`: TimeSpan.FromMinutes(JwtValidationOptions.ClockSkewMinutes)

**JWT Claims Extraction:**
```csharp
public sealed class DynamicJwtPayload
{
    public required string Subject { get; init; }        // JWT subject claim
    public required string EnvironmentId { get; init; }  // environment_id claim
    public required DateTime ExpiresAt { get; init; }    // JWT ValidTo
    public required DateTime IssuedAt { get; init; }     // JWT ValidFrom
}
```

### Error Handling Specifications
[Source: FRD S2 Section 7.1, Exception Handling]

**JWT Validation Error Mapping:**
- `SecurityTokenExpiredException` → `Error.Unauthorized("Token expired")`
- `SecurityTokenException` → `Error.Unauthorized("Invalid token")`
- `HttpRequestException` (JWKS fetch) → `Error.External("Request failed", exception)`
- `TaskCanceledException` → `Error.Timeout("Request timeout", exception)`
- `JsonException` (JWKS parsing) → `Error.Validation("Invalid JSON response")`
- `Exception` (general) → `Error.External("Validation error", exception)`

### Performance Considerations
**JWKS Caching Strategy:**
- Cache raw JSON (not parsed objects) to avoid serialization issues
- Use absolute expiration relative to now (not sliding expiration)
- Handle cache miss gracefully with HTTP fallback
- Log cache hits/misses for monitoring
- Consider cache warming for production environments

**Memory Management:**
- JWKS response typically < 5KB, safe for memory cache
- Cache key collision unlikely with constant key name
- No need for cache size limits at current scale
- Consider distributed cache (Redis) for multi-instance deployments (future)

### Integration with Story 2.1
**HttpClient Dependency:**
- Uses "JwksClient" HttpClient registered in ServiceCollectionExtensions
- No authentication headers needed for JWKS endpoint (public keys)
- Polly retry policies will handle transient JWKS fetch failures
- 10-second timeout sufficient for JWKS retrieval
