# Story 2.6: Add Basic Observability

## Status
**Ready for Review**

## Story
**As a** DevOps engineer,
**I want** essential logging and metrics for Identity operations,
**so that** I can monitor production health and troubleshoot issues.

## Acceptance Criteria

1. Add structured logging with correlation IDs to all handlers
2. Add basic metrics: `exchange_success`, `exchange_failure` (ETag metrics via existing global counters)
3. Log critical events: JWT validation failures, rate limit hits, wallet conflicts
4. Ensure all logs include correlation IDs for request tracing

### Technical Details from Architecture

**Observability Framework** [Source: architecture/14-observability-epic-2-production-grade.md]:
- **OpenTelemetry Implementation**: Comprehensive tracing from API → Application → Domain → Infrastructure
- **Correlation IDs**: Propagated across all layers, included in logs and responses
- **Required Epic 2 Metrics** already defined:
  - `identity_exchange_success_total` (counter) - Successful exchanges by provider
  - `identity_exchange_failure_total` (counter) - Failed exchanges by error type  
  - `identity_etag_hits_total` (counter) - ETag cache hits (304 responses)
  - `identity_etag_misses_total` (counter) - ETag cache misses (200 responses)
  - `identity_rate_limit_hits_total` (counter) - Rate limit violations by IP

**Structured Logging Requirements** [Source: architecture/14-observability-epic-2-production-grade.md]:
```json

  "timestamp": "2025-09-11T15:30:45.123Z",
  "level": "Information", 
  "message": "Exchange completed successfully",
  "correlationId": "01JA2B3C4D5E6F7G8H9J0K1L2M",
  "traceId": "abc123def456",
  "principalId": "01JA2B3C4D5E6F7G8H9J0K1L2M",
  "provider": "dynamic",
  "walletsProcessed": 2,
  "walletsLinked": 1,
  "created": false,
  "requestDuration": 156.7
}
```

**Privacy Compliance in Logging** [Source: architecture/14-observability-epic-2-production-grade.md]:
- **NEVER log**: Email addresses, phone numbers, contact identifiers
- **Safe to log**: Principal IDs, wallet IDs, chain IDs, addresses (public blockchain data)
- **Always include**: Correlation IDs for request tracing

**Tech Stack Requirements** [Source: architecture/3-tech-stack-final.md]:
- **Observability**: OpenTelemetry .NET for traces, logs, metrics → OTLP
- **Logging**: Structured logger with OTel enrichment, no Console.WriteLine

**Coding Standards** [Source: architecture/16-coding-standards-minimal-critical.md]:
- **Logging**: Use structured logger with OTel enrichment; no Console.WriteLine
- **PII**: No contact identifiers persisted or logged; tests must assert this

**Performance Requirements** [Source: architecture quality requirements]:
- Structured logging must not significantly impact API response time target: <200ms
- Metrics collection should be lightweight and non-blocking
- Correlation ID propagation must be efficient across request pipeline

**Security Requirements** [Source: architecture/15-security.md]:
- Never log contact identifiers or PII in any log statements
- Safe to log public blockchain data (addresses, chain IDs) and internal IDs
- Correlation IDs should not contain sensitive information
