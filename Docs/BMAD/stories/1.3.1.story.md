# Story 1.3.1: Application Layer Cleanup (Remove Overengineered Code)

## Status
**Completed** - Ready for Review

## Story
**As a** backend engineer,  
**I want** to clean up the Identity Application layer by removing overengineered and unnecessary code,  
**so that** the codebase aligns with our minimal MVP requirements and maintains clarity for future development.

## Acceptance Criteria
1. **Remove overengineered orchestration layer:** Delete DynamicAuthOrchestrator and related services that don't align with our direct CQRS implementation approach.
2. **Eliminate outdated DTOs:** Remove CommandResponse DTOs and other response objects not needed for our two-endpoint MVP (`POST /auth/exchange`, `GET /auth/me`).
3. **Clean up obsolete specifications:** Remove specifications that reference outdated domain model properties from pre-Story 1.3 implementation.
4. **Preserve essential base classes:** Keep BaseIdentityCommandHandler, BaseIdentityQueryHandler, and BaseIdentityIdempotentCommandHandler as they provide value for CQRS pattern.
5. **Update command handler:** Simplify ExchangeTokenCommandHandler to work without orchestrator while maintaining placeholder for Story 1.4 implementation.
6. **Ensure compilation:** Application layer must compile successfully with no references to deleted components.

## Integration Verification
- IV1: Application layer compiles without errors or warnings
- IV2: No references to deleted services remain in DI registrations
- IV3: ExchangeTokenCommand and GetCurrentUserQuery remain functional with proper handlers
- IV4: Domain layer integration preserved - no domain functionality affected

## Context

After implementing Story 1.3 (Domain Aggregates & Invariants), we established a clean domain model following DDD principles. However, the Application layer contains significant overengineering from previous iterations that conflicts with:

- **PRD Requirements**: Only 2 endpoints needed (`POST /auth/exchange`, `GET /auth/me`)
- **Architecture Decision**: Stateless design with direct CQRS pattern
- **Domain Model**: New aggregate structure created in Story 1.3 with different properties than old specifications expected
- **MVP Scope**: Minimal persistence without contact identifiers or complex profile metadata

The cleanup ensures Story 1.4 (Exchange Command Handler implementation) can build on a clean foundation.

## Technical Implementation Notes

### Orchestration Layer Removal Rationale
The `DynamicAuthOrchestrator` represented an overengineered approach that:
- Added unnecessary abstraction layers
- Conflicted with direct CQRS command handling approach
- Made the codebase harder to follow and maintain
- Wasn't aligned with the PRD's simple two-endpoint design

### Domain Model Alignment
Many specifications and DTOs were using properties that don't exist in the new domain model from Story 1.3:
- Old: `principal.Profile.Language.Value` → New: Domain doesn't have Profile aggregate
- Old: `wallet.Chain` → New: `wallet.ChainId` 
- Old: `ownership.ProofType` → New: `ownership.Status` (enum-based)
- Old: `ownership.IsDeleted` → New: Domain uses proper aggregate lifecycle
