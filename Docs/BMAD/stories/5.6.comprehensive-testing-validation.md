# Story 5.6: Comprehensive Testing & Validation

## Status
**Draft**

## Story
**As a** Backend Developer,
**I want** to implement comprehensive test coverage for all Epic 5 critical scenarios including network environment isolation, per-environment exclusivity, query performance, and security validations,
**so that** we have complete confidence that our identity persistence and constraints system works correctly across all edge cases and maintains data integrity.

## Acceptance Criteria
1. **NetworkEnvironment Isolation Tests**:
   - Same base58 address on mainnet vs devnet = different Wallet rows
   - No index conflicts between network_environments
   - Same (chain_id, address) across network_environments → same principal; wallets are network_env-scoped
2. **Per-NetworkEnvironment Exclusivity**:
   - Two verifies on same `(network_env, wallet)` → one winner
   - Two verifies on different network_env wallets → both succeed
3. **Query Performance**:
   - EXPLAIN ANALYZE shows index scans for `(network_env, chain_id, addr)`
   - EXPLAIN ANALYZE shows index scans for `(provider, issuer, subject)`
4. **Default Guard Tests**:
   - Default on mainnet doesn't affect devnet
   - Setting default requires verified+signing on that env
5. **Other Critical Tests**:
   - JWKS rotation: seamless kid1 → kid2 transition
   - Challenge TTL and clock skew handling
   - Replay detection across instances
6. **API Enhancement**:
   - /auth/me returns wallets grouped or tagged by {network_environment, chain_id} so integrators can render per-network state easily
7. **Query Plan Validation**:
   - Assert all hot paths use index scans via EXPLAIN ANALYZE in CI pipeline
   - CI gate fails if any critical query uses seq scan instead of index scan
8. **Address Normalization Tests**:
   - Address normalization prevents duplicates from format differences
   - Invalid address formats rejected at API edge
9. **Multi-Tenant B2B Security Tests**:
   - Partner A's Dynamic token rejected for Partner B's API key
   - Partner A's wallet signature rejected when `aud` = Partner B
   - Same wallet can be verified by different partners (different aud)
   - Cross-app replay prevented via audience binding
   - **nbf/exp skew acceptance within ±60s**
   - **Namespaced replay keys prevent cross-API-key collisions**
   - **Cross-network-env attach requires verified+signing (not watch-only)**
   - **EXPLAIN CI gate confirms index scans on all hot paths**

## Dev Notes

### Testing Framework and Standards
[Source: architecture/17-testing-strategy.md]
- **Unit Testing**: NUnit + Shouldly for domain aggregates, invariants, and application handlers
- **Integration Testing**: NUnit with Testcontainers for real PostgreSQL testing
- **Coverage Targets**: Domain & Application ~80% lines, emphasize branch coverage for invariants
- **No-op guards**: Must be explicitly verified in tests

### Database Schema Constraints to Test
[Source: architecture/10-database-schema-postgresql-16-ef-core-9.md]
- **Unique Indexes** (must test for constraint violations):
  - `ux_wallet_netenv_chain_addr`: `(network_environment, chain_id, address)` WHERE `is_deleted=false`
  - `ux_credential_provider`: `(provider, issuer, subject)` WHERE `is_deleted=false`
  - `ux_ownership_pair`: `(principal_id, wallet_id)` WHERE `is_deleted=false`
  - `ux_exclusive_signing`: `(wallet_id)` WHERE `status='verified' AND access_mode='signing'`
  - `ux_chain_default`: `(principal_id, network_environment, chain_id)` WHERE `is_deleted=false`

### Critical Test Scenarios from Epic Requirements
[Source: Epic 5 requirements]
1. **Environment Isolation**: Same wallet address must create separate rows per network environment
2. **Exclusive Signing**: Only one verified+signing owner allowed per wallet (database enforced)
3. **Deterministic Resolution**: Tie-break order must be consistent (dynamic_attested > direct_signature_msg > direct_signature_tx > watch_only)
4. **Transaction Semantics**: Row-level locking must prevent race conditions
5. **Cross-Environment Attach**: Must validate verified+signing ownership across environments

### Testing Standards
[Source: architecture/16-coding-standards-minimal-critical.md]
- **No PII**: Tests must assert no contact identifiers are persisted or logged
- **Structured Logging**: Use OTel-enriched logger, no Console.WriteLine
- **Error Handling**: Business failures return Result, don't throw for expected states
- **IDs**: Test ULID generation and CHAR(26) storage

- **Database Testing**: Testcontainers with PostgreSQL 16
- **Mocking**: NSubstitute for external dependencies
- **Redis Testing**: Redis test container for replay protection
