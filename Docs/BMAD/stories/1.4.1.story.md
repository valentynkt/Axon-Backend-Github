# Story 1.4.1: ExchangeTokenCommand Full Implementation Integration

## Status
Draft

## Story
**As a** backend engineer,  
**I want** ExchangeTokenCommand to properly parse JWT tokens and delegate to ExchangeCredentialCommand for business logic,  
**so that** the `/auth/exchange` endpoint provides a complete end-to-end implementation while maintaining clean separation of concerns.

## Acceptance Criteria
1. **JWT Processing**: ExchangeTokenCommandHandler parses and validates JWT tokens, extracting user data including wallets and provider information.
2. **Integration Layer**: ExchangeTokenCommand serves as API-facing layer that calls ExchangeCredentialCommand internally to leverage existing business logic.
3. **Error Mapping**: Proper error handling with appropriate HTTP status codes (400/401 for JWT issues, 409 for conflicts, etc.).
4. **Validation**: Update ExchangeTokenCommandValidator to ensure JWT token is present and properly formatted.
5. **Contract Compatibility**: Existing API contracts remain unchanged - `/auth/exchange` endpoint continues to work as expected.

## Integration Verification
- IV1: `/auth/exchange` endpoint successfully processes Dynamic.xyz JWT tokens end-to-end
- IV2: ExchangeTokenCommand validates JWT and delegates to ExchangeCredentialCommand for business logic
- IV3: Error responses map correctly to HTTP status codes with appropriate error messages
- IV4: API contracts remain unchanged from client perspective

### JWT Processing Requirements  
[Source: architecture.md#JWT-Authentication]
- **Provider**: Dynamic.xyz JWT tokens with JWKS validation
- **Claims Usage**: Extract `iss`, `sub`, and wallet data; ignore contact claims (email, etc.)
- **Validation**: Use `JwtBearerHandler` + `ConfigurationManager` for JWKS rotation
- **Caching**: JWKS cached with ~1h TTL and proactive refresh
- **Security**: No contact identifiers should be persisted or logged

### API Specifications
[Source: architecture.md#API-Contracts]
- **Endpoint**: `POST /auth/exchange` with `Authorization: Bearer <JWT>` header
- **Rate Limiting**: 10 requests/min per IP
- **Response**: ExchangeOutcome with operation metrics (AxonId, Created, WalletsProcessed, etc.)
- **Error Codes**: 400 (malformed), 401 (invalid/expired), 409 (conflict), 422 (business rule), 429 (rate limit)

### Integration Architecture
[Source: architecture.md#Commands]
- **ExchangeTokenCommand**: API-facing layer for JWT processing
- **ExchangeCredentialCommand**: Internal business logic layer  
- **Flow**: JWT → Parse/Validate → ExchangeUserData → ExchangeCredentialCommand → ExchangeOutcome
- **Error Handling**: Use Result pattern, map to appropriate HTTP status codes
