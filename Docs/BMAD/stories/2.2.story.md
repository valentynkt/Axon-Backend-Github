## Status
**Ready for Review**

## Story
**As a** client application,  
**I want** HTTP ETag caching on `/auth/me` endpoint,  
**so that** I avoid unnecessary data transfers when my principal data hasn't changed.

## Acceptance Criteria
1. `MeEndpoint` reads `If-None-Match` header and passes to query
2. `GetMyPrincipalQuery` accepts optional `IfNoneMatch` parameter  
3. Handler returns `304 Not Modified` when ETag matches current fingerprint
4. Successful responses include `ETag` header with principal fingerprint
5. Include `Cache-Control` headers for caching guidance
6. Test complete flow: 200 → 304 → data change → 200

## Integration Verification
- IV1: `/auth/me` returns 200 OK with ETag header on initial request
- IV2: Subsequent request with matching `If-None-Match` returns 304 Not Modified
- IV3: Request with outdated `If-None-Match` returns 200 OK with new ETag
- IV4: Cache-Control header includes `private, max-age=0, must-revalidate`
- IV5: ETag changes only when principal data actually changes (verified ownerships, defaults, or principal itself)

### Technical Details from Architecture

**ETag Implementation** [Source: architecture/13-caching-etags.md]:
- **ETag for `/auth/me`**: Compare `If-None-Match` vs DB fingerprint; return **304** if unchanged
- **Cache-Control**: `private, max-age=0, must-revalidate` (frontend always validates with ETag)

**API Specification** [Source: architecture/8-rest-api-specification-epic-2-production-ready.md]:
- **If-None-Match parameter**: Header parameter for conditional GET support
- **200 Response**: Includes ETag header with deterministic fingerprint
- **304 Response**: Not Modified - ETag matched If-None-Match, includes Cache-Control headers
- **ETag format**: Deterministic fingerprint for conditional GET (e.g., `"sha256-abc123..."`)

**Database Schema** [Source: architecture/10-database-schema-postgresql-16-ef-core-9.md]:
- **ETag Fingerprint**: Combines `principal.updated_at` + verified signing ownership + chain defaults
- **Determinism**: Pending-only ownership changes, `last_seen` touches don't affect ETag
- **SQL Implementation**: SHA256 hash of concatenated timestamps as hex string

**Core Workflow** [Source: architecture/7-core-workflows.md]:
- **ETag Optimization Flow**: FindByCredential → GetPrincipalFingerprint → Compare → Return 304 or load data
- **Smart Detection**: Avoids full data load when ETag matches
- **Observability**: Metrics for etag_hit and etag_miss events

### Technical Constraints

**HTTP Specification Compliance** [Source: architecture/8-rest-api-specification-epic-2-production-ready.md]:
- ETag header format must be quoted string (e.g., `"sha256-abc123"`)
- If-None-Match comparison should be case-insensitive
- 304 responses must include Cache-Control but not the response body
- Cache-Control must specify `private, max-age=0, must-revalidate`

**Performance Requirements** [Source: architecture/9-application-layer-cqrs-catalog-epic-2-simplified.md]:
- Use compiled queries for fingerprint generation
- Avoid N+1 queries in ETag computation
- Skip full data loading when returning 304 Not Modified
- Single round-trip for ETag comparison

**Determinism Requirements** [Source: architecture/10-database-schema-postgresql-16-ef-core-9.md]:
- ETag must change only when relevant data changes
- `last_seen` touches must NOT affect ETag
- Pending ownership changes must NOT affect ETag
- Only verified & signing ownership changes affect ETag
