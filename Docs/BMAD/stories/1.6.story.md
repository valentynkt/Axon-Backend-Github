### Technical Details from Architecture

**Error Response Schema** [Source: architecture.md#rest-api-specification]:
```json
{
  "code": "WALLET_OWNERSHIP_CONFLICT",
  "message": "wallet already owned", 
  "details": {
    "chainId": "solana",
    "address": "base58-address-here"
  }
}
```

**HTTP Status Code Mapping** [Source: architecture.md#error-handling-strategy]:
- `400`: Malformed JWT/request
- `401`: Invalid/expired JWT  
- `409`: Wallet ownership conflict (verified & signing already owned)
- `422`: Business rule violation (non-conflict)
- `429`: Too Many Requests (rate limit)
- `500`: Unexpected error

**Privacy Requirements** [Source: architecture.md#error-handling-strategy]:
- **Privacy for 409**: Response MUST NOT include any principal identifiers other than the caller's
- Use `ApiError.details = { chainId, address }` only
- **Logging**: Include correlation ID, principal id (when resolved), provider and wallet identifiers **without PII**

**OpenAPI Security Configuration** [Source: architecture.md#rest-api-specification]:
```yaml
securitySchemes:
  bearerAuth:
    type: http
    scheme: bearer
    bearerFormat: JWT
    description: "Provider-issued JWT (e.g., Dynamic.xyz)"
```

**Rate Limit Headers** [Source: architecture.md#rate-limiting]:
- `Retry-After`: seconds until rate limit reset
- `X-RateLimit-Remaining`: remaining requests in current window  
- `X-RateLimit-Reset`: timestamp when rate limit resets
- Return with 429 status when rate limit exceeded

### Technical Constraints

**Error Envelope Consistency** [Source: architecture.md#error-handling-strategy]:
- All error responses must use consistent `ApiError` envelope format
- Error codes must be meaningful strings, not HTTP status codes
- Messages should be human-readable but not expose internal system details

**Privacy and Security** [Source: architecture.md#security]:
- Never expose other users' Principal IDs in error responses
- Log full context for debugging but return safe information to clients
- Maintain audit trail while protecting user privacy

**API Documentation Standards** [Source: architecture.md#tech-stack]:
- Support both Swagger and Scalar UI for developer choice
- Comprehensive examples for integration guidance
- Proper authentication configuration with JWT bearer tokens
- Error schemas documented with realistic examples

**Module Isolation** [Source: Axon Backend Architecture]:
- Identity module API documentation must not interfere with other Axon modules
- Shared error handling patterns should be extensible for other modules
- Security headers and CORS configuration must remain consistent
