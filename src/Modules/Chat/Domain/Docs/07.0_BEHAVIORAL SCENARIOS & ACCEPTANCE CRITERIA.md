# 07\_BEHAVIORAL SCENARIOS & ACCEPTANCE CRITERIA (MVP)

This doc turns our state model and rules into executable-style acceptance criteria. It’s domain-only: no API, no persistence, no infra. Use it to drive tests (GWT), detect gaps, and keep behavior crisp.

---

## 1) Scenario Matrix (at a glance)

| Capability            | Happy Path                                                     | Key Rejections                                                                                         | Event Emitted            |
| --------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------ |
| Start Conversation    | Start with defaulted title; Start with user title              | Invalid ownerId; Title length out of bounds (if provided)                                              | ConversationStarted      |
| Append Message        | First user message; Assistant after user; User after assistant | Not Active; First is assistant; Consecutive assistant; Content len out of bounds; Max messages reached | MessageAppended          |
| Update Title          | Change to new title                                            | No effective change; Length out of bounds                                                              | ConversationTitleUpdated |
| Complete Conversation | Complete Active with ≥1 message                                | Already Completed; Empty conversation                                                                  | ConversationCompleted    |

## 2) Start Conversation

### S1.1 Start with defaulted title

* **Given** a valid `ownerId`
* **And** no title provided (or empty/whitespace)
* **When** starting a conversation
* **Then** conversation is `Active`
* **And** `title = "New chat {shortId}"`
* **And** `isDefaultTitle = true`
* **And** `messageCount = 0`
* **And** `ConversationStarted` is raised with `(conversationId, ownerId, title)`

### S1.2 Start with user-provided title

* **Given** a valid `ownerId`
* **And** `title` length is between 1 and 200 (trimmed)
* **When** starting a conversation
* **Then** conversation is `Active`
* **And** `title = provided (trimmed)`
* **And** `isDefaultTitle = false`
* **And** `ConversationStarted` is raised

### S1.3 Reject invalid ownerId

* **Given** `ownerId = Guid.Empty` (or invalid)
* **When** starting a conversation
* **Then** operation is rejected with `CHAT.CONVERSATION.OWNER_REQUIRED`

### S1.4 Reject invalid title length when provided

* **Given** `title` length > 200 or == 0 after trim
* **When** starting a conversation
* **Then** rejected with `CHAT.CONVERSATION.TITLE_INVALID`

## 3) Append Message

### S2.1 First message must be user

* **Given** an `Active` conversation with `messageCount = 0`
* **When** appending `role = "user"` and `content` length in \[1..100\_000]
* **Then** message is created with `sequence = 1`, `occurredAt = now`
* **And** `MessageAppended` is raised with `(conversationId, messageId, sequence=1, role="user", contentPreview(100), contentLength)`

### S2.2 Reject assistant as first message

* **Given** `Active` with `messageCount = 0`
* **When** appending `role = "assistant"`
* **Then** rejected with `CHAT.MESSAGE.FIRST_MUST_BE_USER`

### S2.3 Alternate: assistant after user

* **Given** `Active` with last message `role="user"`
* **When** appending `role="assistant"` with valid content
* **Then** appended with `sequence = last.sequence + 1`
* **And** `MessageAppended` is raised

### S2.4 Alternate: user after assistant

* **Given** `Active` with last message `role="assistant"`
* **When** appending `role="user"` with valid content
* **Then** appended; event raised

### S2.5 Reject consecutive assistant

* **Given** `Active` with last message `role="assistant"`
* **When** appending `role="assistant"`
* **Then** rejected with `CHAT.MESSAGE.TURN_TAKING_VIOLATION`

### S2.6 Reject when not Active

* **Given** conversation `status="Completed"`
* **When** appending any message
* **Then** rejected with `CHAT.CONVERSATION.NOT_ACTIVE`

### S2.7 Reject content length out of bounds

* **Given** `content.Length = 0` or `> 100_000`
* **When** appending
* **Then** rejected with `CHAT.MESSAGE.CONTENT_INVALID`

### S2.8 Reject when max messages reached

* **Given** `messageCount = 10_000`
* **When** appending a message
* **Then** rejected with `CHAT.CONVERSATION.MESSAGE_LIMIT_EXCEEDED`

---

## 4) Update Title

### S3.1 Update to a new, valid title

* **Given** a conversation (Active or Completed)
* **And** `title length ∈ [1..200]` after trim
* **And** differs (case-insensitive) from current
* **When** updating title
* **Then** `title` changes, `isDefaultTitle = false` (MVP)
* **And** `ConversationTitleUpdated` is raised with `(conversationId, oldTitle, newTitle)`

### S3.2 Reject no effective change

* **Given** new title equals current after trimming and case normalization
* **When** updating
* **Then** rejected with `CHAT.CONVERSATION.TITLE_NO_CHANGE`

### S3.3 Reject invalid title length

* **Given** `newTitle` length not in `[1..200]` after trim
* **When** updating
* **Then** rejected with `CHAT.CONVERSATION.TITLE_INVALID`

---

## 5) Complete Conversation

### S4.1 Complete an active conversation with ≥1 message

* **Given** `status="Active"` and `messageCount ≥ 1`
* **When** completing
* **Then** `status="Completed"`, `completedAt=now`
* **And** `ConversationCompleted` is raised with `(conversationId, ownerId, messageCount)`

### S4.2 Reject completing empty conversation

* **Given** `status="Active"` and `messageCount = 0`
* **When** completing
* **Then** rejected with `CHAT.CONVERSATION.EMPTY_CANNOT_COMPLETE`

### S4.3 Reject completing an already completed conversation

* **Given** `status="Completed"`
* **When** completing
* **Then** rejected with `CHAT.CONVERSATION.NOT_ACTIVE`

## 6) Decision Tables

### D1: Turn-taking (previousRole → newRole)

| previousRole    | newRole   | Allowed | Reason                                |
| --------------- | --------- | ------- | ------------------------------------- |
| — (no messages) | user      | ✅       | First must be user                    |
| —               | assistant | ❌       | First must be user                    |
| user            | user      | ✅       | Allowed (user can send consecutively) |
| user            | assistant | ✅       | Alternation allowed                   |
| assistant       | user      | ✅       | Alternation allowed                   |
| assistant       | assistant | ❌       | No consecutive assistant              |

> MVP rule: **only** assistant is constrained from consecutive turns.

### D2: Append eligibility

| status    | messageCount | contentLen    | Allowed | Error                    |
| --------- | -----------: | ------------- | ------- | ------------------------ |
| Active    |     0..9,999 | 1..100,000    | ✅       | —                        |
| Active    |       10,000 | any           | ❌       | MESSAGE\_LIMIT\_EXCEEDED |
| Active    |          any | 0 or >100,000 | ❌       | CONTENT\_INVALID         |
| Completed |          any | any           | ❌       | NOT\_ACTIVE              |

## 7) Event Emission Rules (domain-level)

* **ConversationStarted**: emitted exactly once during start.
* **MessageAppended**: emitted exactly once per successful append. Payload includes:

    * `(conversationId, messageId, sequence, role, contentPreview(100), contentLength, occurredAt)`
* **ConversationTitleUpdated**: emitted only when a real change occurs.
* **ConversationCompleted**: emitted exactly once upon successful completion.

> No aggregate version in event payload (MVP). Infra may enrich envelopes later.

---

## 8) Property-based / Invariant Tests (suggested)

* **Sequence contiguity**: for any sequence of `AppendMessage` that pass, `messages[i].sequence == i + 1`.
* **First is user**: after any valid sequence with ≥1 message, `messages[0].role == "user"`.
* **No consecutive assistant**: for all i>0, not (`messages[i-1].role == "assistant"` and `messages[i].role == "assistant"`).
* **Status/Completion**:

    * If `status == Completed` then `completedAt != null` and `AppendMessage` always rejects.
    * If `status == Active` then `completedAt == null`.
* **Title constraints**: `title` never empty; length always in `[1..200]`.
* **Message constraints**: each message content length in `[1..100_000]`.

---

## 9) Edge & Fuzz Scenarios

* Titles with leading/trailing whitespace → trim; evaluate length and equality post-trim.
* Titles with case-only changes → considered “no change”.
* Content with only whitespace → invalid (length after trim == 0).
* Very long content → reject at 100,001.
* Rapid alternating appends still enforce sequence contiguity and turn-taking.
* Completes immediately after first append → valid; prevents further appends.

---

## 10) Acceptance Checklist per Operation

**Start**

* [ ] ownerId valid
* [ ] title chosen (defaulted vs provided) and within `[1..200]`
* [ ] status = Active, messages empty
* [ ] ConversationStarted emitted

**Append**

* [ ] status = Active
* [ ] turn-taking rule satisfied
* [ ] content length in range
* [ ] messageCount < 10,000
* [ ] sequence = previousCount + 1
* [ ] MessageAppended emitted with preview(100) and length

**UpdateTitle**

* [ ] new title in range
* [ ] differs after trim + case-fold
* [ ] title updated; isDefaultTitle updated (MVP → false)
* [ ] ConversationTitleUpdated emitted

**Complete**

* [ ] status = Active
* [ ] messageCount ≥ 1
* [ ] status set to Completed; completedAt set
* [ ] ConversationCompleted emitted
